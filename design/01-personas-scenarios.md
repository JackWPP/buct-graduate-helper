## 1. 三个画像（按"打开动机"分，不按年级分）

| 画像 | 典型时点 | 打开动机 | 一次成功的样子 | 失败的样子 |
| --- | --- | --- | --- | --- |
| **开学型**（研一，9 月） | 收到通知后、晚上 | 我下一步该办什么、什么时候截止 | 注册 / 培养计划 / 选课 / 交材料四件事一次办完 | 不知道有这件事，或错过截止 |
| **日常型**（研一—研二） | 早上出门、课间、睡前 | 今天在哪上课、下节是什么 | 3 秒内看到教室 | 走错楼、记错周次 |
| **节点型**（研二—博士） | 导师提一句之后、deadline 前一周 | 我的流程走到哪、卡在谁手上 | 看到节点状态 + 缺什么材料 | 材料被退回但没通知 |

**关键结论**：三类人的打开动机完全不同 → 首页不能是同一套固定模块。"全体研究生"不等于"所有人看同一屏"，而是**同一套结构，内容随阶段与人变**。这正是 S0 §5 阶段驱动槽位的依据。

## 2. Jobs 四象限

| | 低利害 | 高利害 |
| --- | --- | --- |
| **高频** | 看今天课、查教室、切周次 | 考试安排、临时调课、成绩发布 |
| **低频** | 各类登记、证明打印、申请入口 | **选课**、注册、培养计划提交、开题 / 中期 / 查重 |

设计含义，按象限给不同标准：

- **高频低利害 → 0 摩擦**。不许登录态等待、不许首屏空转、不许二次点击才看到课。桌面小组件是这个象限的正确答案。
- **低频高利害 → 0 犯错**。余量、冲突、格式、截止全部前置算好，提交前把不确定项全部摊开。
- **高频高利害 → 主动推送**。这类场景用户不会主动查，只能推。
- **低频低利害 → 能找到就行**。搜索 + 宫格 + WebView，不做深。

> 一个反面提醒：PRD 把 48 个 GMIS 页面都做成入口，但按这个矩阵，其中约 30 个属于"低频低利害"，**投在设计上的边际收益极低**。L2 覆盖、不做深，是对的。

## 4. 选课的结构性发现（来自接口，非猜测）

这四条决定了选课页的形态，比"筛选器长什么样"重要得多：

1. **计划内 / 计划外是两套逻辑**，不是两个筛选项。计划内 = 培养方案里的课（必修 + 按方向选修），计划外 = 跨选。真实用户先看计划内，再考虑计划外。→ **选课页应是两个 Tab，不是一张混在一起的列表**。
2. **每次提交都要一个验证码**（`codetype=xkyzm`，独立于登录验证码）。提交失败也要重来。→ **选课页的核心不是"列表好看"，是"减少提交次数"**。每减少一次提交，就减少一次验证码 + 一次失败风险。
3. **课程规模三级跳**：当前选课窗口内 12 门 → `kb_list` 265 门 → 全校总目录 772 门。→ 12 门时不需筛选器，772 门时必须有。**默认视图按当前窗口出，筛选器折叠**。
4. **失败返回的是 `{"msg":"..."}` 文本**，没有结构化错误码。→ 客户端必须做一层**失败原因归一化**（余量满 / 时间冲突 / 不在选课时间 / 门数超限 / 已选过），否则直接把后端中文怼给用户。

## 5. 由此产生的设计决策（进 S2 前先定）

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 选课页分「计划内 / 计划外」两个 Tab | 对应两套接口与两套心理模型 |
| D2 | 列表项必须显示：余量（53/60）、冲突标记、学分、周次/节次 | 这三项决定用户要不要点进去提交，能挡掉大部分无效提交 |
| D3 | 提交前做"一次性确认"：把所有风险摊在一张卡上（冲突 / 余量紧张 / 门数超限） | 一次确认胜过三次失败重试 |
| D4 | 验证码预取 + 失败不清空筛选与已填信息 | 减少重复劳动，这是"高效"的实质 |
| D5 | 课表页不做装饰，只做可读性；桌面小组件列为 P0 而非 P1 | 高频低利害象限的标准答案 |

## 6. 已确认的三条事实（2026-11-02）

| 问题 | 结论 | 对设计的直接影响 |
| --- | --- | --- |
| 选课边界 | 提醒 + 筛选 + **Agent 推荐与计算** + **抢课能力** | 选课不再是列表页，而是「方案 + 抢课队列」。新增 3 个界面 + 1 套状态机 |
| 失败主因 | **余量被抢走**、**时间冲突**（验证码错与掉登录不在前列） | 这两项必须在**列表层前置**，不能留给错误态。"提交前确认"升为核心页面 |
| 课表导入 | WakeUp 已适配北化教务，**我们也要做适配** | 课表不是护城河——用户手上已有一个能自动导入的工具。我们必须至少一样好用，并把数据以 WakeUp 能吃的形式交出去 |

## 7. 推荐与抢课：已定（2026-11-02）

**推荐只做一件事：照着研究生手册和培养方案，算出"你还差哪几门、这几门什么时候上、会不会撞"。**

- 用得到的数据：培养方案要求的学分结构、已修课程、课程开课周次与节次、余量、教师、校区。
- 用不到、也不做的：课程好不好、给分高不高、作业多不多。GMIS 里没有这些，硬编就是假的，用户第一次用就会发现。
- 不做社区、不做评价、不做排行榜。

**抢课做"半自动 + 极速验证码"**：用户点开始 → App 自动提交队列第一门 → 弹 4 位验证码 → 输错自动刷新并重试同一门 → 失败原因直接写清楚。全程用户看得见、随时能停。

## 8. 一条需要记住的事实

WakeUp 没有对第三方开放的写入接口，它能吃的是教务系统内置适配、分享口令、Excel、图片/文件四类。所以"我们也要做适配"= **把 GMIS 数据解析好，再以它能吃的形式交出去**（ICS / Excel / 分享图），不是"替 WakeUp 适配"。
